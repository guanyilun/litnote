#+title: litnote: literate org notes for any analysis project
#+OPTIONS: toc:2 num:nil ^:{}

Shared tooling for programs and analyses explained through org notes.
Organize the source around the ideas a reader needs to understand, refine
those ideas into executable code, and connect important claims to evidence.
The documents are the source of truth for computational reasoning and
analysis code; explanatory visuals can be maintained separately in
=diagrams/=. Tangled code and rendered pages are outputs.

Cheap computations can run in a live Python session with =#+RESULTS:=.
Expensive steps are tangled to scripts, run externally, and their reports
included back. The HTML brings prose, mathematics, code and evidence
together with linked Noweb chunks and a comment layer for review.

* Investigation and explanation

Projects have two kinds of document:

- =analysis/= holds working investigations, organized by exploration and
  execution dependencies. Keep inputs, commands, results and decisions
  recoverable, including useful failed trials. A polished narrative is not
  required for every step.
- =note/= holds standalone explanations, organized around a coherent
  question, algorithm or argument. Connect purpose, assumptions, reasoning,
  implementation and evidence. Preserve relevant uncertainty and contrary
  evidence when presenting conclusions.

A note can draw on several analyses, and an analysis can support several
notes. Link to or include authoritative material rather than maintaining
copies. Core algorithms and their explanations belong in =note/=; their
reusable implementations tangle to =src/= and are imported by analyses.

Review each document individually. =readme.org= links to them and records
status; there is no combined review document in new projects. =RUN_NOTES=
in the Makefile lists documents with run cells in dependency order,
independently of the index or presentation order. Discovery currently covers
top-level =.org= files in each directory.

* Design for understanding

Start with the problem, the intended reader's background, inputs, outputs
and assumptions. Write explanatory notes for a beginning graduate student
in the relevant field: assume general undergraduate preparation, introduce
specialized terminology, define mathematical symbols, and explain the
intermediate reasoning. Present the governing idea and the roles of its main
components, then refine them beside their implementations. Top-down
exposition is a useful default; choose another order when a definition or
example first makes the reasoning clearer.

Think of the conceptual structure, the computational dependencies, and the
exposition connecting them. They need not have identical shapes. A reader
should be able to find how an idea is implemented and why an important
operation belongs in the algorithm. Ordinary headings, prose, equations,
named chunks and references express these connections; no graph annotations
or readability scores are required.

- Give each major component a meaningful responsibility and explain its
  contribution to the whole.
- Explain decisions, assumptions, boundary cases and significant state
  changes. Connect mathematical symbols and units to code identifiers.
- Extract a Noweb chunk when its name clarifies the surrounding argument.
  Keep simple code visible when a jump adds no insight. Functions provide
  callable interfaces; chunks reveal implementations in explanatory stages.
- Actively use diagrams and plots to explain mechanisms, relationships and
  algorithmic structure. Prefer readable SVG diagrams for conceptual visuals;
  introduce each figure and explain what connection it reveals.
- Keep correctness arguments and focused checks near the claims they
  support. Explain what those checks do and do not establish.
- Review the overview before expanding every chunk: can the intended reader
  explain the main reasoning, locate assumptions and evidence, and predict
  a relevant behavioral change? Report specific gaps with concrete revisions.

The scaffold demonstrates this with a weighted mean, its input contract,
and checks of equal weighting and translation. The full authoring and
review guide is in =doc/claude-project.md=. These presentation requirements
apply to explanatory notes; working analyses have the lighter requirements
above.

Named chunks free explanatory order from tangled source order. Session
blocks and run cells still require dependency order; =make runs= follows
=RUN_NOTES= and each document's cell order.

* How the pieces fit together

A project is a directory with =note/*.org= and =analysis/*.org=, a small =Makefile= that
includes =mk/litnote.mk=, and whatever the notes tangle and the runs write.
Cheap steps are notebook cells (see "The notes daemon" below): edit, run
in the session with =bin/note=, and the result sits under the block.
Expensive steps go around this loop:

#+begin_example
   analysis/x.org ──make tangle──▶ bin/ src/ scripts/ ──run (shell, queue)──▶ out/…/report.txt, *.png
        ▲                                                                        │
        │                                                  #+INCLUDE / [[file:]] │
        │                                                                        ▼
   edit the note ◀──comments (.org)── review in browser ◀──make── out/notes/*.html
#+end_example

1. *Write* a step in a note: a paragraph saying what and why, then the code
   in bare blocks with =:tangle /abs/path=. Refine meaningful concepts
   beside their explanations, using named chunks to assemble source order.
2. *Tangle* (=make tangle=) and *run* the script outside Emacs; it writes a
   report file (and figures) under =out/=.
3. *Show* the run in the note: a =:run= cell with the exact command, then
   =#+INCLUDE:= of the report.  Write the prose from that output.
4. *Render* (=make=): every note becomes =out/notes/<source-path>.html=, labelled
   as notebook cells (=→ path=, =▶ run=, =output=);
   documents in =note/= and =analysis/= are reviewed individually.
5. *Rerun* (=make runs=): every run cell of the notes, in order, from the
   inputs; =make runs-list= shows the plan.  A run cell only calls tangled
   scripts, so every result comes from reviewed code.
6. *Check* (=make check-tangled=): every file in =CODE= is tangled from a
   note and none was edited by hand.  Since review happens on the notes,
   this identifies which files have source available in the notes; it
   does not establish that they were reviewed or understood.
7. *Review*: open the page, leave comments in the right margin, and use
   /Copy open/ or /Export .org/.  The comments go back as edits to the
   notes (by you, or by Claude given the exported file), and the loop
   starts again.

The rules that keep this honest (code only in notes, explanations only in
prose, outputs only by include, notes self-contained) are under
Conventions below.

* Starting a project

#+begin_src sh
~/software/litnote/bin/litnote-new ~/work/myproject "Some title"
cd ~/work/myproject && make tangle
mkdir -p out/example && python bin/example.py > out/example/example.txt
make
#+end_src

This writes =Makefile=, =readme.org=, =CLAUDE.md=, an explanatory algorithm
in =note/<name>.org= and an importing investigation in =analysis/<name>.org=,
and links =bin/note=. Run the example before rendering its included report.
The index links to the individual documents. =RUN_NOTES= defaults in the
scaffold to =analysis/<name>.org=; extend it in dependency order as needed.

Existing projects keep support for =notes/=, =REVIEW= and their existing
HTML paths. To adopt the new layout, move documents according to their role,
update links and session commands, replace =REVIEW= with =RUN_NOTES=, and
replace the aggregate document with index links. Check the run plan with
=make runs-list= before executing it.

* Conventions

- *The documents are the reference for analysis code.* Computational files
  are the =:tangle= target of a block in =note/*.org= and =analysis/*.org=; =make check-tangled=
  fails otherwise, and also catches files edited by hand after tangling
  (it restores them and reports).  =CODE= in the Makefile lists the globs
  that count as analysis code.
- *Explanations in prose, not in code.*  No explanatory comments or
  docstrings in tangled blocks; the paragraph above the block says why.
  Only what the code needs functionally (e.g. a =__doc__= used by argparse).
- *Readable names.*  Variables and functions are named for what they hold
  (=noise_var=, not =nv=); single letters only where conventional or where
  they are an equation's symbols, and then defined in the prose beside
  the block.  Code brought in from elsewhere is renamed when it becomes
  the note's code.
- *Plain prose.*  Write a note the way you would explain the analysis to a
  colleague: what we want to know and why, what we did, what we found.
  Short sentences with one idea each, no chains of semicolons and nested
  parentheses, the takeaway first in a results paragraph, terms defined in
  plain words, and numbers said in words when that helps ("about a
  third").  The full guide is "Writing the prose" in =doc/claude-project.md=.
- *Explanation and implementation together.* Choose block boundaries by
  conceptual responsibility. Put rationale beside the relevant code or link
  explicitly to it. Blocks sharing a =:tangle= path concatenate in order;
  named Noweb chunks allow a different explanatory order. Put =:shebang=
  on the first tangled block only.
- *Visual explanation.* Actively use figures to clarify important concepts
  for a beginning graduate student. Standalone SVGs and optional scripts
  used only to draw explanatory diagrams can live in =diagrams/=; their
  source does not need to appear in the note or be tangled. Keep them in
  version control and outside analysis =CODE= globs. Result-producing code
  still follows the analysis workflow. Each figure has a =#+NAME:= and
  =#+CAPTION:=; introduce it in the prose and explain the connection it
  reveals. Use absolute image paths for inlining in the current exporter.
- *Refine ideas with Noweb.* An outline with =:noweb yes= names meaningful
  components, such as =<<validate measurements>>=. Each is a named block
  with no =:tangle= and =:eval no= for source fragments, beside its
  explanation. Tangling supplies the reference's indentation, and the page
  links references to chunks and back. Length alone does not require
  extraction; avoid needless fragmentation. Reusable behavior belongs in
  library functions, whose implementations can themselves use chunks.
- *Header.*  =#+PROPERTY: header-args :mkdirp yes :comments link :eval no=,
  absolute =:tangle= paths.  Use =:comments no= on blocks whose language
  Emacs =-Q= has no comment syntax for (YAML), or the link line corrupts the
  file.
- *Runs read as cells.*  A run is a =#+begin_src sh :run <where> :eval no=
  block holding the exact command, which writes a report file, followed by
  =#+INCLUDE: "/abs/path/report.txt" example=.  Never paste output by hand.
  Figures: =[[file:...png]]= after the run that saved them, with a
  =#+NAME: fig:x= and a =#+CAPTION:= written like a paper's.  The caption
  only describes what is plotted (data, selection, axes, units, colours,
  markers), which the code fixes; what the figure shows goes in the results
  text, which cites it as =Figure [[fig:x]]= and is backed by the report.
- *Individual documents.* Use =readme.org= as an index and review each
  document's HTML. Reading order is independent of =RUN_NOTES= execution
  order. Include or link evidence at its authoritative location.
- *Self-contained.*  Identify inputs and how to reproduce them. Links between this
  project's notes and analyses are encouraged; avoid relying on unexplained
  files from other projects or colleagues' working directories.  Scientific references are fine.
- *Equations* as =\( \)= / =\[ \]= with =^:{}= in =#+OPTIONS=.

* What the export does

=make= renders every note and =readme.org= to =out/notes/{note,analysis}/*.html= and =out/notes/readme.html=, one
self-contained file each (figures inlined as base64).  A project Makefile can
set =OUTDIR= to render elsewhere.  Legacy =notes/x.org= renders flat to
=$(OUTDIR)/x.html=, keeping old URLs; =LEGACY_FLAT := no= keeps it in
=$(OUTDIR)/notes/= beside =note/= and =analysis/=, and links follow.


- Export never runs babel (=org-export-use-babel nil=); it shows what is in
  the buffer or included from files.
- Tangle blocks are labelled =→ path= (relative to the project root, the
  directory above =note/= or =analysis/=); =:run= blocks =▶ run (where)=; the example block
  after a run, or a =#+RESULTS:=, =output=.  A block that a =:noweb= outline
  includes is labelled =⟨name⟩ in → path=; each =<<name>>= in the outline
  links to it, and the name in its label links back to the outline.
- A figure can have frames: =#+ATTR_HTML: :data-frames /abs/b.png /abs/c.png
  :data-labels first|second|third= on its image (no quotes; labels joined
  by =|=, the image itself first).  The frames are inlined with the image,
  and =j= / =k= (or the buttons under it) step the figure nearest the middle
  of the screen.  Print and the static image show the first frame, so make
  it the one the text relies on.
- Code blocks longer than 28 lines are shown in a box of about 18 lines
  that fades out at the bottom, with a bar under it ("▾ show all 61 lines")
  that expands it and folds it back.  Following a link into a clamped block
  expands it; print shows every block whole.
- Outputs are folded by default, under a line giving their length
  ("39 lines"); a click opens them.  They open by themselves for printing,
  when they carry a review comment, and when a comment is opened from the
  Comments panel.
- Pygments highlighting (python, sh, yaml, org, json, elisp, make).  The
  token markup depends on the pygments version, so build under the project's
  environment for reproducible HTML.
- MathJax 3.
- Before each export =check-results.py= warns about evaluated blocks with no
  output, =check-excerpts.py= about quoted output that no longer matches,
  =check-rebinds.py= about session variables rebound between blocks.

* Review comments

Every exported page carries a comment layer: hover in the right margin of
any paragraph, block or figure and click =+=.  Comments are kept in the
browser (localStorage, per page) and anchored by section title, block kind
and a text snippet, so they survive re-rendering; a comment whose text was
rewritten shows as "anchor not found".  To comment on particular words,
select them within one block and click the /Comment/ button that appears:
the comment is anchored to the block in the same way and keeps the selection
as its quote, highlighted on the page while the comment is open.  The
Comments button opens the panel:
- *Copy open* puts the open comments on the clipboard as org TODOs, then
  offers to mark them resolved;
- *Export .org* downloads all of them (TODO/DONE) and *Import* reads such a
  file back.

* Working with Claude

=doc/claude-project.md= is the same workflow written as instructions for an
agent: the loop, the rules, how to act on exported review comments, the
pitfalls, and what "done" means.  Each project's =CLAUDE.md= imports it
with =@/path/to/litnote/doc/claude-project.md= and adds only what is
specific to the project (environment, job submission, data), so changing
the guide here changes it for every project.  =CLAUDE.md= at the top of
this repo is for work on litnote itself.

When Claude Code runs on another machine and reaches the project over ssh,
the import cannot be followed; point that machine's =CLAUDE.md= at the
project's, to be read over ssh at the start of a session.

* The notes daemon

For cheap steps, the note is a notebook: python blocks evaluated in one
live session, held by an Emacs daemon so it survives between commands:

#+begin_src sh
bin/note start              # emacs --daemon=note-<project>
bin/note open analysis/x.org
bin/note stale              # blocks changed since the last run, and empty results
bin/note run                # re-run from the first changed block
bin/note py 'print(x)'      # evaluate in the note's interpreter
bin/note stop
#+end_src

=lisp/babel-setup.el= makes python tracebacks show up in =#+RESULTS:=
instead of an empty result.

* Installing

Clone the repo once per machine; projects use the checkout in place, so
any location works (the examples here use =~/software/litnote=):

#+begin_src sh
git clone <repo-url> ~/software/litnote
#+end_src

=make= needs Emacs with org (tested with Emacs 27.2 / org 9.4 and Emacs 31.1) and a
=python3= with pygments; build under the project's environment, since the
pygments version changes the highlighted HTML.  The notes daemon needs
=emacsclient=.  Rendered pages load MathJax from a CDN.

To update, =git pull= in the checkout; every project picks up the change
on its next =make=.
